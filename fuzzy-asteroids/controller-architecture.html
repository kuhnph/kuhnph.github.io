Fuzzy Logic Controller Architecture

How navigation, obstacle avoidance, and vehicle control work together.

This document describes the current high-level architecture of the fuzzy controllers used for the Asteroids project. The game simulation remains separate from the control system, while a navigation layer converts the raw game state into a temporary waypoint that Peach can follow.

High-Level Architecture

                  +----------------------+
                  |      Game Engine     |
                  |----------------------|
                  | Entity State         |
                  | Physics              |
                  | Collision Detection  |
                  | Rendering            |
                  +----------+-----------+
                             |
                             | Serialized Game State
                             ▼
                  +----------------------+
                  |  Navigation Layer    |
                  |----------------------|
                  | Asteroid Filtering   |
                  | Fuzzy Avoidance      |
                  | Fuzzy Look-Ahead     |
                  +----------+-----------+
                             |
                             | Pseudo-Target Position
                             ▼
                  +----------------------+
                  |  Vehicle Controller  |
                  |----------------------|
                  | Heading Control      |
                  | Speed Control        |
                  +----------+-----------+
                             |
                             | Discrete Actions
                             ▼
                  +----------------------+
                  |      Game Engine     |
                  |----------------------|
                  | Rotate Peach         |
                  | Accelerate Peach     |
                  | Update Physics       |
                  +----------------------+

The current system uses three fuzzy controllers:

  1. Avoidance controller — chooses an angular offset around an asteroid.
  2. Look-ahead controller — chooses how far ahead to place the waypoint.
  3. Vehicle controller — turns and accelerates Peach toward that waypoint.

Separation of Responsibilities

Game Engine

Responsible for:

  • Entity positions and velocities
  • Movement and damping
  • Rendering
  • Collision detection
  • Target spawning and capture
  • Applying controller actions

The game exposes a snapshot through:

state = game.get_entity_states()

The snapshot contains ordinary Python values for Peach, the target, asteroids, and bullets. An entity state may look like:

{
    "position": [x, y],
    "velocity": [vx, vy],
    "radius": radius,
    "direction": [dx, dy]
}

The game accepts controller decisions through:

game.play_step(
    ship_actions=[],
    peach_actions=actions
)

Possible Peach actions are:

clockwise
counterclockwise
accelerate
no action

Navigation Layer

Responsible for converting the target and asteroid states into a safe temporary waypoint. It:

  1. Computes target-relative and asteroid-relative geometry.
  2. Filters asteroids using predicted trajectory and target threats.
  3. Selects one relevant asteroid.
  4. Uses fuzzy avoidance to choose a direction offset.
  5. Uses fuzzy look-ahead to choose a waypoint distance.
  6. Produces the pseudo-target position.

The position is constructed as

\[ P_{pseudo} = P_{Peach} + d_{lookahead} \hat{t}_{rotated} \]

where the direct target direction is rotated by the fuzzy avoidance offset.

Vehicle Controller

Responsible for steering Peach toward the pseudo-target. It derives:

heading_error
distance_error
speed

and evaluates the vehicle fuzzy controller:

outputs = vehicle_controller.evaluate({
    "heading_error": heading_error,
    "distance_error": distance_error,
    "speed": speed,
})

The fuzzy outputs are desired_turn_rate and desired_speed. The current action adapter uses the sign of the desired turn rate to choose a fixed clockwise or counterclockwise rotation. It accelerates only when desired speed is greater than current speed.

The Three Fuzzy Controllers

1 — Avoidance Controller

asteroid_clearance ──┐
                     ├──► avoidance_offset
asteroid_bearing ────┘

asteroid_clearance is the current center-to-center distance minus Peach’s radius, the asteroid radius, and a safety margin. asteroid_bearing is measured relative to the direct target direction.

The controller generally turns away from an asteroid on either side, chooses a hard-right convention for an asteroid directly ahead, and reduces avoidance for asteroids categorized as far away.

2 — Look-Ahead Controller

target_distance ─────┐
                     ├──► pseudo_target_distance
asteroid_clearance ──┘

The waypoint is placed farther ahead for a distant target and shortened when the selected asteroid is near or critical. The result is never allowed to extend beyond the actual target.

3 — Vehicle Controller

heading_error ──┬────► desired_turn_rate
distance_error ─┤
speed ──────────┴────► desired_speed

Heading rules determine the turning output. Heading and distance rules determine desired speed. Speed is currently supplied and fuzzified, but no rule uses it as an antecedent yet.

Shared Fuzzy Controller Pipeline

All three controllers use the same reusable fuzzy engine.

Crisp Inputs
      │
      ▼
Fuzzification
      │
      ▼
Rule Evaluation with min()
      │
      ▼
Output Aggregation with max()
      │
      ▼
Weighted-Average Defuzzification
      │
      ▼
Crisp Outputs

Step 1 — Crisp Inputs

Inputs are ordinary floating-point values such as distance, speed, clearance, or bearing.

Step 2 — Membership Functions

The current implementation uses three shapes:

  • Triangular sets
  • Left-shoulder sets
  • Right-shoulder sets

These shapes describe labels such as near, far, left, aligned, and fast. Their overlap allows one input to belong partly to several sets.

Step 3 — Fuzzification

Each crisp input is evaluated against every set belonging to its variable. For example:

{
    "left": 0.25,
    "aligned": 0.75,
    "right": 0.0
}

Step 4 — Rule Evaluation

Rules store mappings such as:

IF asteroid bearing is left
THEN avoidance offset is right

For a rule containing several antecedents, AND is implemented with the minimum membership:

firing_strength = min(antecedent_strengths)

Step 5 — Aggregation

If several rules recommend the same output set, the strongest firing strength is retained:

aggregated_strength = max(rule_strengths)

Step 6 — Defuzzification

Each activated output set is represented by its center. A weighted average converts the output activations into one crisp value:

\[ y = \frac{\sum_i \mu_i c_i}{\sum_i \mu_i} \]

where \(\mu_i\) is an output activation and \(c_i\) is the center of its fuzzy set. If no output rule fires, the current implementation returns 0.0.

Reusable Fuzzy Class Layout

FuzzyController
│
├── Input FuzzyVariables
│     └── Membership Sets
├── Output FuzzyVariables
│     └── Membership Sets
├── FuzzyRules
├── Fuzzification
├── Rule Evaluation
├── Aggregation
└── Defuzzification

The shared interface is:

crisp_outputs = controller.evaluate(crisp_inputs)

The fuzzy classes do not know whether their values describe a vehicle, asteroid, target, or waypoint. Project-specific variables and rules are assembled outside the generic fuzzy package.

Current Implementation Notes

Heading Units

The vehicle controller calculates the shortest signed heading error and converts it to degrees from -180 to 180. This matches the units used by the heading membership sets.

Continuous Outputs and Discrete Actuation

The fuzzy engine produces continuous numerical outputs. The current game adapter reduces them to fixed rotation and acceleration actions. This keeps the fuzzy engine general while matching the controls exposed by the game.

Genetic Algorithm

Genetic-algorithm experiments exist under the reference code, but the active controller currently uses hand-defined membership sets and rules.

Long-Term Control-System View

The reusable fuzzy inference system still follows the same control-system abstraction:

            Crisp State
                 │
                 ▼
        Fuzzy Inference System
                 │
                 ▼
           Crisp Output

Mathematically,

y = F(x)

where:

  • \(x\) is a dictionary of crisp input variables.
  • \(y\) is a dictionary of crisp output variables.
  • \(F\) is the shared fuzzy inference process.

The surrounding navigation and action-adapter layers decide what those variables mean and how the results affect Peach.
